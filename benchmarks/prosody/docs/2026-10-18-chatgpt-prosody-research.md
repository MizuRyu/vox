Swift
import Foundation

struct LinearHead: Codable, Sendable {
    let weights: [Double]
    let bias: Double

    func score(_ features: [Double]) -> Double {
        precondition(features.count == weights.count)

        var z = bias
        for i in features.indices {
            z += weights[i] * features[i]
        }

        // オーバーフローを避ける sigmoid
        if z >= 0 {
            return 1.0 / (1.0 + exp(-z))
        }
        let e = exp(z)
        return e / (1.0 + e)
    }
}

この score の解釈と判定閾値は、先述の検証・校正で決めます。コードは計算部分の例で、音声処理や学習済みパラメータを含む完成アプリではありません。

最後に：ためらい検知を製品へ入れるべきか

私は、初回製品には「自信のなさを推定して『…』『。。。』を自動挿入する機能」を既定では入れません。疑問符の補正を先に製品化し、ためらいに関する機能は、本人が選ぶ文末表現の候補として実装します。確信度：中〈製品判断〉。

理由は三つです。

聞こえるためらい、本人の内的な自信、文章に残したい表現が一致するとは限らない。 音声の自信研究でも、自己評価と聞き手の知覚、課題による違いを区別しています。確信度：高。 Pon-Barry（2008）、Wilschutほか（2026）。
isca-archive.org
+1
既存データのラベルが、この目的に直接合っていない。 UUDBの信頼軸や、JTESの感情クラスを自己の不確かさへ読み替えることはできません。確信度：高。 UUDB〈2007〉、JTES〈2016〉。
uudb.speech-lab.org
+1
誤った「…」は、本人が文章に残すつもりのなかった態度を加え得る。 その費用を考えると、本人の選択を挟む方が、この一人用アプリでは学習にも製品体験にも合っています。確信度：中〈設計判断〉。

表示は「自信がないと判定しました」ではなく、例えば 「文末表現：…」という選択肢にします。そして、選択・却下の履歴から wantEllipsis を直接学習します。

この進め方なら、最終的に最適化する対象が明確です。声から心情を断定する性能ではなく、本人が直す必要のない文末表現を選ぶ性能を評価し、改善できます。

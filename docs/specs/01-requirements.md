# 01 要件

Vox が満たすべき要件と、二段構成という設計の芯。

最終確認日: 2026-09-07

## 要件

| # | 要件 | 種別 |
|---|---|---|
| R1 | グローバルホットキーで画面下端から HUD がスライドイン | 必須 |
| R2 | 発話内容がリアルタイムに文字表示される | 必須 |
| R3 | 音声入力中にホットキーまたは `@` でコマンドパレットを開く。表示中も音声供給を継続 | 必須 |
| R4 | Enter で選択結果を閉じる時点の本文末尾に挿入する。本文途中で `@` を打った場合はその位置。録音は継続 | 必須 |
| R5 | ユーザー辞書を登録でき、認識結果に反映される | 必須 |
| R6 | 発話中に違和感を覚えた語をその場で訂正できる | 必須 |
| R7 | 完全ローカル。ネットワーク不要 | 必須 |
| R8 | 常駐しても軽い。リッチだが重くない UI | 制約 |
| R9 | 日本語 CER が実用水準（目標: 確定テキストで 7% 前後） | 制約 |
| R10 | 発話中の操作はファイル以外にも拡張できる。sigil でソースを追加できる | 必須 |
| R11 | 訂正機能は feature フラグで無効化できる | 必須 |
| R12 | 発話終了→挿入完了が 500ms を超えない。300ms 以下を目標とする（看板） | 制約 |
| R13 | 初出遅延が 1500ms を超えない。1000ms 以下を目標とする（非看板。最初の 1s は「聞いている」表示で埋める） | 制約 |
| R14 | HUD 表示中はそのまま打てる（割り込み）。打った文字は caret 位置、音声は末尾に追記。録音は止めない。モード切替は設けない | 必須（[ADR-011](../adr/011-hud-edit-mode-and-context-cwd.md) 改訂版） |
| R15 | パレットの検索対象は「トグル ON 時の前面アプリ」から導く。ターミナルならその cwd のリポジトリ | 必須（[ADR-011](../adr/011-hud-edit-mode-and-context-cwd.md)） |
| R16 | 挿入先はトグル ON 時の前面アプリ。確定時にそのアプリを前面に戻してから挿入する | 必須（[ADR-011](../adr/011-hud-edit-mode-and-context-cwd.md)） |
| R17 | 確定したテキストは挿入の成否に関わらずローカル履歴に残り、あとから取り出せる（直近 N 件。私的データなのでリポジトリ外の `~/Library/Application Support/vox/`）。M1 実測で 437 文字の挿入結果が行方不明になった事例が根拠 | 必須 |
| R18 | 確定テキストからフィラー（えっと・あの・うん・文頭の「あ、」等）を規則で除去する。feature フラグで切れる。履歴には生テキストを残す | 必須（[ADR-012](../adr/012-filler-removal-rule-based.md)） |

## 設計の芯 — 二段構成の目的は「精度」ではなく「確定直前の書き換えを消すこと」

初版ではここを「リアルタイム性と精度は単一モデルでは両立しない」と書きました。
調査の結果**その根拠が 2 点とも弱いことが分かったので、二段構成の目的を再定義します**。

**訂正 1 — レーン間の精度差は初版の見立てより小さい。**
初版は速報 CER 13.79% と確定 CER 6.88% を並べましたが、これは**別のデータセットの値を比べていました**
(FLEURS ja と JSUT basic5000)。同一データセットで並べ直すと次のようになります。

| | FLEURS ja CER |
|---|---|
| 速報: Nemotron streaming CoreML @2.24s | 13.79% |
| 確定: parakeet-0.6b-ja CoreML | 10.29% |

差は 3.5pt。2 倍ではありません。

**訂正 2 — 「遅延を削ると日本語が崩れる」も支持されなかった。**
上流 Nemotron の日本語 CER は、チャンクを 1.12s から 80ms まで削っても **11.48% → 13.87% で 2.4pt しか動きません**。
右文脈の欠落が日本語で致命的になるという初版の推論は、実測値では裏づけられませんでした。
モデルカードも「表記遅延は最悪ケースで、平均はその半分」と明記しています。

**では二段構成は不要なのか。必要です。ただし目的が違います。**

理由を 2 層でたどります。

**なぜ単一レーンでは足りないのか。** 3.5pt の差そのものではなく、**書き換えの起き方**が問題です。
ストリーミング単体だと、未確定テキストが表示されたまま何度も書き換わり続ける。
Partial Rewriting の研究 (arXiv:2312.09463) は、この flicker が
「未確定→未確定」の遷移では増える (dictation で +75%) が、
**「最後の未確定→確定」の遷移では 50% 減る**、総合で 13% 減ると報告しています。
つまり二段化の効果は「速報を正確にすること」ではなく「**確定の瞬間の大きな書き換えを消すこと**」です。

**なぜそれが日本語で特に効くのか。** 英語の書き換えは主に語末の追記ですが、
日本語は同音異字のため**表示済みの漢字が別の漢字に差し替わります**。
「こう」を読みに持つ漢字は数百あり、書き換えが視覚的にはるかに目立つ。
確定の瞬間に文がガラッと変わる体験は、遅延そのものより不快になります。

**結論: 2 レーンを並走させる。**

| レーン | 役割 | 表示 |
|---|---|---|
| 速報レーン | 喋った瞬間の追従。書き換わる前提で扱う | 淡色・未確定 |
| 確定レーン | 発話区切りごとに一度だけ上書きし、以後動かさない | 通常色・確定 |

確定テキストは挿入されて手元に残るものなので、そこには最良のモデルを使う。
速報テキストは「今喋れている」というフィードバックであって、正確さの担保ではない。
この役割分担が二段構成の本質です。

現在の本体は速報レーン（Apple）1 本で動いており、確定レーンは未実装です。着手の判断材料は
[02 音声エンジン](02-speech-engines.md)にあります。

# ADR-019: 辞書は表記の完全一致で置換し、読みの正規化と形態素解析は入れない

- 状態: **提案**（2026-09-23）
- 関連: [ADR-012](012-filler-removal-rule-based.md)（フィラー除去は規則ベース）、[仕様 05](../specs/05-text-postprocessing.md)、[仕様 02](../specs/02-speech-engines.md)

## 文脈

実機で「末尾」と言うと「松尾」になる（2026-09-04 の報告、仕様 05）。開発用語が固有名詞に化ける誤認識は、
発話のたびに手で直す必要があり、「喋ったほうが速い」が崩れる。

採用エンジンの Apple `SpeechTranscriber` には語彙バイアスの公開 API が無い（仕様 02）。
したがってデコード段で直す L1 は使えず、**認識後の置換（L2）が唯一の手段**である。

仕様 05 は L2 の実装方式を「確定テキストをカタカナ読みに正規化し、辞書の読みと編集距離で照合して置換」と
書いていた。この ADR はその方式を初版では採らないことを決める。

## 判断

**辞書は「表記 → 表記」の表とし、確定テキストに対して最長一致・完全一致で置換する。**

- 辞書ファイルは `~/Library/Application Support/vox/dictionary.tsv`。1 行 = `置き換える表記<TAB>入れたい表記`。
  `#` で始まる行と空白だけの行は無視する。ファイルが無い状態が「辞書を使わない」状態である
- 照合は Character 単位の完全一致。大小・全半角・読みの正規化はしない。同じ語に表記の揺れがあれば行を足す
- 同じ位置に複数の項目が当たるときは**左辺が長い項目**が勝つ。左辺が重複する行は最初の行だけを採る
- 置換した結果は再走査しない（`A → B`、`B → C` を連鎖させない）
- 右辺は空でよい。「なんか、」→「」のように、規則では消さないと決めた語（ADR-012）を利用者が消せる
- 適用は **フィラー除去の前**、`committed` の追記分に対して。`tentative` と手入力には掛けない
- 履歴の `raw_text` は置換前のまま（ADR-012 と同じ理由。置換は挿入用の変換であって記録を書き換えない）
- 壊れた行（列数が合わない、左辺が空、左辺の重複）はその行だけ落として読み込みを続け、
  設定画面が 1 始まりの行番号で知らせる
- 辞書は録音開始時に 1 度読む。録音中にファイルを変えてもその回には効かない（設定と同じ扱い）

## 理由

**なぜ読みの正規化と編集距離を採らないか。** 4 つある。

1. 読みの取得は Apple の形態素解析辞書（`CFStringTokenizer` の読み属性）に依存する。同じ入力に対する
   読みが OS 更新で変わっても、検査で気づけない。表記の完全一致なら検査が入力と出力を完全に固定できる
2. 読みに落とすと、当たった読みの範囲を元の文字範囲へ戻す対応づけが必要になる。表記一致には無い状態が増える
3. 編集距離を入れると「どれだけ似ていれば置き換わるか」という閾値が増える。誤爆したときの説明が
   「閾値のせい」になり、利用者が辞書を直して制御できなくなる
4. 表記一致なら、利用者は履歴の `raw_text` で見た文字列をそのまま左辺に書ける。揺れが出たときの費用は
   「行を足す」だけで、上限が見える

**なぜ形態素解析を併用しないか。** 仕様 05 が挙げた「松尾さん」の誤爆は実在する。ただし辞書は利用者が
自分で書く表であり、誤爆したら行を消せる。品詞と文脈で適用を絞る仕組みは、辞書サイズと遅延（軸 A は 300ms）と
「なぜ今の行が効かないのか」という新しい説明責任を同時に持ち込む。仕様 05 の「まず素朴な読み置換を作り、
誤爆が実際に出たら形態素解析を足す」という順序をそのまま守り、素朴さの側を表記一致に置き換える。

**なぜフィラー除去より前か。** `FillerPass` の単独フィラーは左側の境界だけを要求するので（ADR-012 の
2026-09-02 改訂）、文頭の「えーあい」は「あい」になる。除去を先にすると、フィラーと同じ音で始まる誤認識は
辞書で直せない。また利用者が左辺に書く文字列は履歴の `raw_text`（除去前）で見た文字列なので、
前に置くほうが対応が 1 対 1 になる。この順序は `CommittedText.clean` に 1 か所だけ置き、本体と検査が同じ実装を通る。

**なぜ TSV か。** 壊れた行だけを落として続ける要件が形式を決めた。JSON は 1 か所の構文エラーで
ファイル全体が読めなくなり、「12 行目だけ直してください」と言えない。行指向の形式なら行番号で言える。
設定は `settings.json` のままで、辞書だけ別ファイル・別形式にする（設定画面で編集する項目ではないから）。

**なぜ機能フラグを足さないか。** ファイルが無い、または行頭に `#` を付ける、が既に切る手段になっている。
`--no-dictionary` は同じことを 2 つ目の方法で実現するだけである。

## 却下した案

| 案 | 却下理由 |
|---|---|
| カタカナ読み + 編集距離（仕様 05 の初版方式） | 上の 4 点。見直しの条件に回す |
| 形態素解析で品詞・文脈を見て適用を絞る | 遅延と辞書サイズ、説明責任が増える。誤爆は行の削除で制御できる |
| 辞書を `settings.json` の配列に入れる | 壊れた行を落として続けられない。設定画面で編集する項目でもない |
| 置換を確定時の全文に 1 回だけ掛ける | HUD の表示と貼り付ける本文が一致しなくなる（ADR-012 の WYSIWYG） |
| 計測 1 行に `dictionary_applied_count` を足す | schema 版とキー数の契約を 1 つの数字のために動かす。履歴の `raw_text` と `inserted_text` の差で同じことが分かる |
| `--no-dictionary` フラグ | ファイルの退避と `#` で足りる |
| 左辺が英数字のときだけ単語境界を要求する | 日本語の認識結果に英数字の左辺はまず現れない。使う前に作らない |
| 置換後に読点・空白を畳む | 辞書は書いたとおりに置き換えるのが説明できる。読点まで消したいなら左辺に入れる |
| 訂正 UI（語のクリック、⌃Z）と辞書候補の自動提案 | 差分の取得・候補の保存・提示 UI が一式必要で、辞書そのものより大きい。辞書が効くと分かってから判断する |

## 結果として受け入れるもの

- 短い左辺（1〜2 文字）は無関係な場所でも置き換わる。「松尾」→「末尾」を入れた人は「松尾さん」も壊れる。
  利用者向けの文書に危険を書き、行を消せば戻ることを示す
- 確定差分の境界をまたぐ語は当たらない（「松」と「尾」が別の認識結果で来た回）。既存のフィラー除去と同じ制約
- 右辺を空にした置換の後、読点が連続して残ることがある
- `tentative` のまま確定に間に合った末尾は、置換も除去も通らない。これは既存の挙動で、この ADR では変えない
- `.tsv` を表計算アプリが開く環境では、保存し直すと形式が変わる。設定画面が「0 件」や行番号で知らせる

## 見直しの条件

- 同じ誤認識を直すために、表記の揺れで左辺を 3 行以上書かないと直らない事例が出たとき
  → 読みの正規化（`CFStringTokenizer` の読み属性）を足す。編集距離はそのさらに次
- 辞書を使っていて「正しい語まで置き換わる」報告が 2 回以上出たとき → 形態素解析での絞り込みを検討する
- Apple `SpeechTranscriber` が語彙バイアスの API を公開したとき、または確定レーンに FluidAudio を入れる
  判断をしたとき → L1 を再評価する（仕様 05 の L1 は現状の採用エンジンでは使えないだけで、否定されたわけではない）
- 辞書の行数が数百を超えて置換が計測に見えるようになったとき → 走査を左辺の長さごとに分ける

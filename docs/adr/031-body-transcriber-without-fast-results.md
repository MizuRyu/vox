# ADR-031: 本文は `.fastResults` を付けない 2 つ目の認識器から取り、表示用の認識器と同じ analyzer に載せる

- 状態: **提案**（2026-10-28）
- 関連: [ADR-030](030-apple-vocabulary-hints-not-adopted.md)（実発話の CER）、[ADR-007](007-latency-measurement-method.md)（`.fastResults` が要る理由）、[ADR-002](002-two-lane-transcription.md)（テキスト契約）、[ADR-020](020-pause-triggered-segment-commit.md)（無音で区切る）、[ADR-010](010-speed-metric-axis-a-apple.md)（発話終了 → 挿入完了）

## 文脈

[ADR-030](030-apple-vocabulary-hints-not-adopted.md) で、本体のライブ認識（CER 3.0%）が、同じ音声をファイルで渡した SpeechTranscriber（1.0%）の約 3 倍誤ることが分かった。
同じデバッグ録音で設定を 1 つずつ変えて切り分けた（正解は ADR-030 と同じ方法で作った 40 本、9,754 字）。

| 構成（SpeechTranscriber） | CER |
|---|---|
| 設定なし | 1.04% |
| `.volatileResults` だけ | 1.04% |
| `.fastResults` だけ | 2.33% |
| 両方（本体の設定） | 2.33% |

差の大半は `.fastResults` だった。音声を 100 ms ずつ実時間で渡しても、ファイルで一度に渡しても、同じ設定なら CER は同じだった。
ところが `.fastResults` を外すと、発話中に結果が出ず HUD が止まって見える（ADR-007）。

実時間で渡した 3 案（入力の終わり → 確定は `finalizeAndFinishThroughEndOfInput` が返るまで）:

| 案 | 本文の CER | 入力の終わり → 確定（中央値 / 最大） | 発話中の表示 |
|---|---|---|---|
| 今の設定 | 2.33% | 80 / 221 ms | 出る |
| 1 つの analyzer に、表示用（両方）と本文用（設定なし）の 2 つを載せる | 1.32% | 131 / 320 ms | 出る |
| `.fastResults` を外す | 1.04% | 176 / 392 ms | 間を置くまで出ない |

analyzer を 2 つ作って同じ音声を並行して渡す案は、本文の CER が 31% に崩れ、27 本目で結果が返らなくなった。

## 判断

1. **1 つの analyzer に SpeechTranscriber を 2 つ載せる。** 表示用は今と同じ `[.volatileResults, .fastResults]`、本文用は `reportingOptions` を空にする。どちらも `.audioTimeRange` を付ける
2. **HUD の確定（committed）は本文用の final だけで作る。** 表示用の final は、本文用の final がその区間まで届くまで淡色（tentative）に残す。区間は結果の `range.end` で突き合わせ、0.5 秒以内のずれは同じ区間とみなす（`SplitTranscript`）
3. committed は追記専用のまま（ADR-002）。打った文字は動かない（`TranscriptBuffer` は変えない）
4. 本文用の結果が入力の終わりまで届いたら、淡色に残る表示用の文字を捨てて、本文用だけを貼る。途中で落ちた回は淡色を含めて貼る（今までと同じ）
5. 無音で区切る（ADR-020）とパレットの締めは analyzer への `finalize(through:)` なので、両方の認識器に同時に効く。淡色が通常色に変わるのは、この締めか本文用の自発的な区切りのとき

## 却下した案

- **`.fastResults` を外す**: 本文は最も正確だが、発話中に HUD に文字が出ない。話した内容を見ながら直す使い方が成り立たない
- **analyzer を 2 つ並行させる**: 上の測定で崩れた。同じ形式の認識器は裏の処理を共有するため、と Apple の文書から推測しているが、原因は確かめていない
- **確定後に録音をまとめて認識し直す**: ファイル認識は 20 秒の発話で約 1 秒かかり、発話終了 → 挿入完了（ADR-010）が崩れる
- **表示用の final を確定にして、本文用で後から書き換える**: committed が追記専用でなくなり、打った文字の位置（T21）が崩れる

## 検証と限界

- CER は 2 つの認識器を載せたファイル給餌の測定で、本体のライブ録音（無音での区切りあり）では測っていない。本体の 3.0% のうち `.fastResults` で説明できない 0.7 ポイントは、無音での区切りが候補で未確定
- 認識が 2 本走る分の CPU・電力・発熱は測っていない。本体は利用者が起動して確かめる
- 淡色が通常色に変わる頻度が下がる（表示用の final では確定しなくなる）。確定のときに淡色の文字と違う本文に置き換わることがある

## 見直しの条件

- 本体のライブ録音で、本文の CER が 2 つにする前より下がらなかったとき。確認は、デバッグ録音を有効にして集めた回の推定正解での CER（ADR-030 の方法）
- 録音中の CPU 使用率や発熱が利用者に分かるほど増えたとき
- Apple が `.fastResults` の精度への影響を変えたとき（同じ録音で、`.fastResults` の有無で CER の差が無くなる）

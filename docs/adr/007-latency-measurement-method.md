# ADR-007: 初出遅延はファイル給餌 + `.fastResults` で測る。定期 finalize とライブモードは使わない

- 状態: **承認**（T7 でライブマイクとの整合を確認済み。2026-09-02 06:45）
- 日付: 2026-09-02
- T7 の結果: `.fastResults` の約 1s 周期はライブマイクでも同じ（発話開始 +1.5s で初出、以後毎秒）。
  自然モード（`.fastResults` なし）はライブでも発話中に発火せず、約 10s のセグメント境界と finalize でのみ届く。
  よって**ファイル給餌 + `.fastResults` が Apple の初出遅延を測る正当な方法**であり、ライブ経路は測定対象として不要
- 関連: M0 の Apple 発火実験記録と結果記録（非公開）追記 03:20〜05:40

## 文脈

決定 3 の合否基準は「初出遅延（発話開始から最初の文字が画面に出るまで）合格 400ms / 許容 600ms」。
Apple `SpeechTranscriber` をファイル給餌で測ると、結果が入力終了後にまとめて届き、初出遅延が音声長と一致してしまった。
一晩で 3 つの誤った仮説を経て原因に到達したので、その経路ごと記録する。

## 判断

1. **CER も初出遅延も、ファイル給餌（実時間ペーシング）で測る。** ライブマイクの測定リグは作らない
2. Apple エンジンは **`reportingOptions: [.volatileResults, .fastResults]`** を既定にする。`.fastResults` は必須
3. 「逐次発火している」と認める判定基準は **2 条件の同時成立**:
   - タイミング: 最初の結果が `入力終了 − 500ms` より前に届く
   - 精度: CER が基準値（疑似音声で 0.158 / 0 / 0）から +0.05 以内
4. 定期 `finalize` による発火は測定手段として**使わない**

## 理由

### なぜ `.fastResults` か（E2 で確定）

これがないと analyzer は高精度優先のモードで動き、`finalize` か入力終了まで結果を溜める。
足すと給餌中に逐次発火し、**CER は 0.158 / 0 / 0 で一切劣化しない**。判定基準の 2 条件を両方満たした唯一の方法。

### なぜ定期 finalize を使わないか（F4）

`finalize` は発火の契機になる（F3、処理オーバーヘッド約 75ms）が、
- 測定値が**設定した finalize 間隔の関数**になる。500ms 間隔なら初出 575ms、200ms なら 275ms。Apple の実力を測っていない
- 強制確定で認識が分断され **CER が 0 → 0.67 に壊れる**
判定基準の条件 2 を入れたのはこの教訓のため。発火だけ早めても精度が壊れれば測定として無効。

なお、給餌ループと同じタスクから `finalize` を呼ぶと**自己デッドロック**する（給餌側が finalize の完了を待ち、finalize 側は入力の処理進行を待つ）。別タスクから呼べば解ける。使わないが、知見として残す。

### なぜライブマイクのリグを作らないか

`.fastResults` でファイル給餌のまま逐次発火するので、同一音声を両エンジンに与えられ、比較が公正で再現性がある。マイクの個体差・部屋の音・読み上げのばらつきが入らない。
ただし **Apple の「自然モード」（`.fastResults` なし・マイク tap で逐次発火する挙動）はファイル給餌では観測できない**（E7 で確定。`prepareToAnalyze` / `SpeechAnalyzer.Options` / `.audioTimeRange` のどれも発火条件ではなく、差は入力源にある）。これだけは最小プローブ（T7）で 1 分測る。**リグではなく観測プローブ**。

### 経た誤りと、それぞれの反証

| 仮説 | 反証 |
|---|---|
| result reader が actor を継承し給餌と executor を共有している | detached task に分離しても結果は変わらず（入力終了の 52.7ms 後に一斉到着） |
| Apple はライブでないと逐次発火しない | `finalize` で発火するので liveness は要件ではない。さらに `.fastResults` で解決 |
| 位相を制御すれば初出の期待値を 0.65s にできる | 発話開始を 3250 / 3500ms にずらして 782 / 1446ms。tick 周期に加え「発火に足る音声量（500ms では不足）」の条件があり、600ms は切れない |

## 判明した Apple の性質（測定結果の解釈に必要）

- `.fastResults` モードは**約 0.9〜1.0s 周期の tick** で、**仮説が変わったときだけ**発火する
- tick 時点で発火に足る音声量が必要。500ms 分では不発、782ms 分で発火
- よって初出遅延は **782〜1446ms**。決定 3 の基準を満たさない
- 処理そのものは速い（finalize あたり約 75ms）。遅いのではなく溜めている

## 測定の前提条件（守らないと値が無効になる）

- 給餌は絶対 deadline 方式のペーシング（相対 sleep はドリフトが累積する）。ドリフト 1〜6ms を確認済み
- `AVAudioFile` は analyzer の `commonFormat` / `isInterleaved` で開く。既定の processingFormat で開くと結果が空になる
- `AVAudioFile.length` は実データより多く報告されることがある。末尾 4ms 相当の read 失敗は EOF として扱う
- manifest の `speech_start_ms` を正しく入れる。先頭無音があると初出遅延に乗る
- 正解テキストは ADR-008 の規約に従う。表記の揺れを実力と誤認する

## 見直しの条件

- T7 で自然モードの発火周期が 1s より短いと分かったとき → 自然モードを測るためのライブ経路を、**測定対象として**追加する（このとき初めてリグが必要になる）
- Apple が発火周期を制御する API を公開したとき
